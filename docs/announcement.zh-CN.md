# 标题

开源 TaskQuay：让 ChatGPT 调度本地 Codex，补上任务台、Token 回执和受控并行

# 正文

大家好，最近我一直在尝试一种开发方式：让 ChatGPT 做主控，负责分析问题、安排任务和验收，再让本机的 Codex 处理适合委派的代码工作。

能跑通以后，我发现真正影响体验的，不只是模型会不会写代码，还有一堆工程上的小问题：任务多了以后，不容易看清哪些是主控下发的；一个问题拆成好几个代理，各自重新理解一遍上下文；几个任务同时写文件、同时编译，反而产生返工；聊天已经结束，却不知道它究竟用了多少 Codex Token、验收有没有真正完成。

所以我基于 **[Waishnav/DevSpace](https://github.com/Waishnav/devspace)** 做了一些二开，整理成 **TaskQuay**。先说明出处：不是从零造出来的，上游已经提供了很好的本地 MCP 执行基础，这个分支主要补我在长程开发里遇到的管理、成本和可靠性问题。

**项目地址：[github.com/wrfgup/taskquay](https://github.com/wrfgup/taskquay)**

## 核心思路：主控先读，确有需要再让 Codex 干活

很多背景调查根本不必先叫一个 Codex 出来。主控可以直接通过 MCP 看目录、读相关源码、搜索文本、检查现成日志和测试回执。

确实需要 Codex 时，再给它一份边界明确的任务：目标是什么，哪些代码相关，已经确认了什么，还需要验证什么。后续修正尽量继续同一个相关会话，而不是每一步都新开一个。

当然，主控看过的东西如果又全文粘给 Codex，仍然会消耗 Codex 输入 Token。这里想省的是重复探索和无关上下文，不是靠换一种传输方式宣称“免费”。

## 这次主要补了什么？

**一个按项目看的任务台。** 默认本机访问 `/console/`，可以看任务来源、执行状态、验收证据、关联 Codex 会话和用量。主控直接完成、没有调用 Codex 的任务也能留下记录。

**任务结束有一份 Token 回执。** 统计接的是 provider 的用量事件，不是根据回答长度猜。完整、部分、未知、未调用分别显示；拿不到统计不能装成零，整个会话过去的消耗也不能都塞到最新任务里。数字不等于订阅余额或账单。

**并行不是越多越好。** 纯只读任务可以有限并行，默认最多两个；同一工作目录的写入保持独占，共享构建输出和设备另做资源协调。任务超额在本地排队，不让模型消耗 Token 去“等别人”。

**会话复用与项目级整理。** 相关工作优先继续已有线程，独立审查则允许新上下文。受管会话有统一来源标记，归档／恢复先预览项目范围，再确认执行；活动任务、外部续写和归属不明的聊天默认跳过，不把你的其他 Codex 聊天当垃圾清理。

## 几个必须说清楚的边界

这是早期项目，不是一个“装上就全自动交付”的产品，也没有测出可以保证的固定 Token 节省比例。

本地运行不代表所有内容永不离开电脑：主控收到的文件内容、委派给模型的材料，都需要遵守对应服务的权限和隐私约定。Shell 依然使用本机用户权限，工作区路径校验和任务锁不是万能沙箱。

归档方面，安全流程和夹具测试已经有了，但此前的零推理空线程实测没有完成真实恢复验证。正式依赖这个功能前，请先在自己的 Codex 实例里用明确的新测试会话跑通，不要拿重要聊天试验。归档也不等于停止后台进程。

目前对外叫 TaskQuay，但兼容命令和配置目录仍保留 `devspace`。建议按仓库的双语 README 从本分支源码运行，不要把上游 npm 包误当成已经包含这些改动的发行版。
